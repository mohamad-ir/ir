## Stack (verified)
- Laravel 13.x, PHP 8.3+, Filament 5.10 (Livewire 4), Tailwind CSS 4, Vite (build-time only)
- MariaDB 10.11 locally (target: MySQL 8 / MariaDB 10.6+ on DirectAdmin)
- No Node.js, Redis, Docker or daemons at runtime. Cron (`schedule:run`) for newsletters/backups; web-cron fallback.

## Scope decisions
- v1.0: Phase-1 exclusions honoured. v1.1 (owner request): paid membership, course sales and live webinars added.
- Payments: Stripe Checkout (hosted page, PCI SAQ-A) via a small REST client (`App\Services\Payments\StripeClient`, no SDK). Audience is international/EU → Stripe; VAT-inclusive prices, optional Stripe Tax, VAT-ID collection, EU withdrawal-waiver consent.
- Live webinars run on Zoom/YouTube Live/Teams; the site handles registration, payment, ICS invites, reminders, private join link, recordings.
- Uploads stored in `public/media` (no storage:link symlink needed on shared hosting).
- First-party cookieless analytics (daily-rotating visitor hash) + optional GA4 (consent banner) + GA4/Search Console reporting via service account.

## Verification log (2026-11-10, 1.4.1 — installer fix)
- Report: fresh 1.4.0 on Laravel Herd → `/install` 500 “Database file database/database.sqlite does not exist”, `.env` containing only `APP_KEY`.
- Root cause (present since 1.0, more likely on servers that run requests in parallel — Herd/nginx + PHP-FPM — when the browser sends several first requests): `bootstrap/prepare-env.php` copied `.env.example` non-atomically; a parallel request read the half-written `.env`, found no key and overwrote it with only `APP_KEY`. Without `SESSION_DRIVER`/`DB_CONNECTION`, Laravel's defaults (database sessions on SQLite) then failed on the installer's first request. Reproduced with the released 1.3.0 and 1.4.0 packages: 1/30 runs with 8 parallel workers, and 100 % with an `APP_KEY`-only `.env`.
- Fix: `prepare-env.php` writes under an exclusive lock via a temporary file + rename, and before installation fills in settings missing from `.env` from `.env.example` (existing values and the key kept; an installed site's `.env` is never extended); until installation is finished, sessions/cache use files and the queue is synchronous regardless of `.env`.
- Verified: `php artisan test` → 309 passed (5 new: create, repair APP_KEY-only, installed site untouched, 12 concurrent runs, installer works with a broken database default); old vs new script under 12 parallel processes: 2/40 vs 0/40 broken; test package built from the fix (not a release): APP_KEY-only `.env` → `/install` 200 and `.env` repaired (Herd-style `oct-academy/public` and DirectAdmin `public_html`), 30 rounds of 8 parallel first requests → 0 broken, full web install on MariaDB → site 200, installer 404, 80 public pages crawled without errors.

## Known limitations (not claimed as done)
- Dashboard Persian translation covers all screens found by crawling every dashboard page plus static extraction; texts inside rarely used modals that cannot be crawled are translated from code but were not all viewed one by one. Dates in Persian use Gregorian month names (no Jalali calendar).
- SVG logos/icons are deliberately not accepted (script risk).
- Popups: no A/B testing and no custom HTML/CSS (by design, for security); statistics are anonymous counts (no unique-visitor figures per popup); frequency and “already seen” state are per browser (a visitor on two devices may see a popup twice; private windows start fresh); exit intent on touch screens is approximated by a quick scroll up.
- Forwarded IP addresses are trusted only from private networks and Cloudflare by default; sites behind another proxy/CDN must set `TRUSTED_PROXIES` (documented in DEPLOYMENT, upgrade 1.3 → 1.4).
- PWA: installation tested in Chromium and with emulated Android/iPhone only; iOS has no install prompt API (instructions are shown), iOS may evict offline data after weeks without use, and Firefox desktop cannot install websites. Push notifications are prepared in the worker but not implemented (needs VAPID keys, subscription storage and a sending job).
- Comments are plain text (links auto-linked, no images or formatting) and have one level of replies. There is no automatic spam service (e.g. Akismet); spam control is approval of first comments, link/word holds, rate limits, a honeypot and member reports.
- Stripe integration is tested against faked API responses only — run one test-mode purchase on the live server before accepting real payments.
- EU VAT compliance (OSS registration, Stripe Tax) is the owner's responsibility; the site supports it but cannot decide it.
- Course videos are protected by access checks and private Vimeo/unlisted YouTube links, not DRM; lesson downloads are in the public media folder (unguessable names, but not access-controlled).
- Discount coupons are managed in Stripe, not in the dashboard. Certificates have no QR code (the verification URL and ID are printed).
- GA4 Data API / Search Console reporting: implemented (service-account JWT) but **not tested against live Google accounts** — no credentials available in the build environment.
- Visitor country stats need a GeoLite2-Country.mmdb upload (or Cloudflare `CF-IPCountry`).
- Demo images are synthetic (generated, labelled) and the doctor profile/CV is placeholder text — replace before launch or run `cms:demo --remove` / the dashboard "Remove demo content" action.
- The web installer is reachable by anyone until installation completes — install immediately after upload (it locks itself afterwards).
- Self-hosted video on shared hosting is limited by disk/bandwidth; YouTube/Vimeo embeds are recommended.
- Phase-1 exclusions (payments, paid memberships, course sales, live webinars, paid gating) are intentionally not implemented; `access_level` + `ContentAccess` and "register interest" lists are the extension points.
